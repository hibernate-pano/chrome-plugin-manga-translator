## 三、遇到的问题（报错、阻塞、意外行为）

1. **Agent 报告的 shape-C import 绕过，第一次测出来是"被拦住了"** ——
   但我追查后发现那是**巧合**：content.ts 里 `export { ... }` 块的贪婪正则
   匹配恰好把另一条 import 顺带扫到了。构造一个干净的最小复现后，shape C
   **确实被漏掉**。如果不追这一步，就会得出"这条不成立"的错误结论。

2. **首次探针（usage-store 累加器）测出来的记录是空的** —— 存储 key 是
   `manga-translator-usage-v1`（模板占位符），我按 `manga-translator-usage` 去读
   自然读不到。改了 key 后才拿到真实数据。

3. **第一版累加器探针测出"没有丢"** —— 因为第二个 context 是 hydrate
   **之后**才写入的，走的是 merge 路径。真正的 bug 需要**两个 context 在
   hydrate 之前就各自持有旧状态**（这正是 worker 与设置页同时打开的情形）。
   改成并发 hydrate 后立刻复现：120 token 变成 10 token。

4. **`pnpm build` 在干净 clone 上第一次就红** —— 不是产品问题，是 clone 里
   没有 `.env`，`inject-env-config.mjs` 写了空占位符，而我的探针代码
   引用了不存在的默认导出。TS 编译器先拦住了。

5. **第 4 个 agent（安全）超时未完成** —— 两次 interrupt 后仍无输出，最终
   关闭。安全面我自己补了：SSRF 绕过形态实测、import 形态矩阵实测、
   干净 clone 的门禁时序实测。**它的缺位不影响结论完整性**。

## 四、最终结果（成功 / 部分完成及具体产出）

**状态：成功**（体检完成，发现 5 个 P0 + 9 个 P1）。

### 最重要的三个发现

**1. 记账累加器会被过期上下文抹掉（P0，已复现）**

`src/stores/usage-store.ts:812` 的 `unionRecords` 对累加器是**替换**语义。
worker 记了 120 token，一个 hydrate 更早的上下文再记一笔，它那份不含
worker 数据的快照就把 120 覆盖成了 10：

```
after worker write:    acc-2026-10 byDay tokens=120
after stale ctx2 write: acc-2026-10 byDay tokens=10   <- 120 消失
FINAL summary: {"translations":1,"billableCalls":1,"tokens":10}
```

用户看到的账单**比真实的少，而且不可恢复**。这与该文件头部注释声称已经
解决的问题直接冲突 —— 修的是明细记录，累加器这条路径没修。

**2. `GET /models` 超时被记成计费调用，且每 15 分钟触发一次（P0，源码确认）**

`src/providers/openai-compatible-base.ts:346`：`/models` 是列举接口，模型
根本没跑，但 408 时记了一笔账单。而同文件 `:412` 的 `probeChatCompletion`
（真 completion、真花钱）408 却不记 —— **两处判断正好反了**。
更糟的是 `allowBillableProbe: false`（设置页每 15 分钟的健康轮询用的正是
这个参数）只挡住了 404 分支，挡不住这条。

**3. 凭据边界的源码门禁有三种 import 形态被整个跳过（P0，已复现）**

`scripts/check-release-consistency.mjs:340-349` 用正则判断 type-only。
实测矩阵：

| 形态 | 结果 |
| --- | --- |
| `import { X } from '...'` | CAUGHT |
| `import X from '...'` | CAUGHT |
| `import * as X from '...'` | CAUGHT |
| `import X, { type Y } from '...'` | **MISSED** |
| 缩进的 import | **MISSED** |

**但是** —— 这是最重要的一步 —— 我把真实 `.env` 放进 clone 跑完整构建，
**产物门禁（`checkNoCredentialsInContentScript`）拦住了**：

```
[release-check] dist/content.js contains a build-time API key
[release-check] the content script is injected into every page the user visits...
ELIFECYCLE Command failed with exit code 1
```

**所以这条不是"能泄漏密钥"，而是"第一道门在 CI 的干净 checkout 上是空转
的，给出虚假绿灯"。** 第二道门是真的。修法是把 `--source-only` 挪到
`inject-env-config.mjs` 之后。

### 推翻 / 纠正的 agent 结论

- **「P2-7 `attemptedImages` 永不回收」是错的** —— `content.ts:343` 确实清了。
  只有 `artworkWatchers` 没清。
- **「凭据边界三种形态被跳过 = 可泄漏密钥」过重** —— 产物门禁拦住了。真实
  严重级别是「第一道门空转」。
- **`vitest.config.ts` 漏跑测试**不成立 —— 磁盘 81 个测试文件 vs
  `vitest list` 81 个，双向 diff 为空。历史上的 `src/popup/` 事故没有重演。

### 顺带确认健康的部分

- **SSRF 防护扎实**：17 种绕过形态实测，十进制/八进制/十六进制 IP、
  IPv6 映射地址、localhost、metadata host 全部拦下。唯一放行的是
  `127.0.0.1.nip.io` 这类 DNS 重绑定 —— 代码注释里明确写了无法在此防。
- **凭据闸门的判据正确**：`isExtensionPageSender` 用 `sender.url` 前缀而不是
  「有没有 tab」，且有真实 content script sender 的反向测试。
- **主记账路径干净**：一次请求只记一次，content script 层已完全退出记账。
